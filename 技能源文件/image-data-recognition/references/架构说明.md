# 架构说明 —— 表格图片转录工作流

> 给非计算机专业的人看的版本。讲清三件事：**怎么运作、为什么这样设计、出错怎么办。**

---

## 一、这个系统是干什么的

一句话：**把表格图片变成"可以放心用来算数、做图表"的 Excel，并且把原图自动归档。**

它要解决的实际问题：
- 表格数据靠人工抄进 Excel 又慢又容易错（不管是车间单据、报销单还是实验记录）；
- 抄错一个数字，后面的统计、开会用的图表全是错的，而且很难发现；
- 照片散落在手机、微信里，过几天想查"当时那张原始单子长什么样"就找不到了。

系统做的就是这三件事，并且保证**任何一个数字都能追溯到原始图片**。

**它不绑定行业。** 表格长什么样（有哪些列、哪些必填、有没有合计、同类词怎么归类）
写在 `schemas/` 的"版式契约"里；裁判脚本本身是通用的。
换一种新表格，只需要新增一份契约，不用改代码。

---

## 二、整体架构（一看就懂）

这一版（V2.0）最大的结构性变化：**AI 从"眼睛 + 手"缩成了"只有眼睛"**，
它和裁判之间**插进了一层确定性脚本**——AI 不再直接产出 `raw.json`。

```
        你（唯一的业务裁判）
         │ 扔照片            ↑ 一次性集中审核
         ↓                   │
   ┌─────────────────────────────────────┐
   │       Codex + 云端视觉模型           │   ← "眼睛"：
   │   看图，交一小段"我看到了什么"        │      只负责"看到什么"
   │   （识别片段：行 + 原文 + 看不清清单） │      编号/换算/必填一律不碰
   └─────────────────────────────────────┘
         │ 识别片段（每张图一小段 JSON）
         ↓
   ┌─────────────────────────────────────┐
   │       脚本层（tools/）               │   ← "手"：
   │  建任务 / 提交识别 / 注册表型 /       │      负责"把看到的东西
   │  导入审核 / 导出长表 / 收尾报告       │      变成规规矩矩的数据"
   │  ——确定性代码，同样的输入给同样的输出  │      格式不合格当场退回，不落盘
   └─────────────────────────────────────┘
         │ raw.json（脚本写、脚本管）
         ↓
   ┌─────────────────────────────────────┐
   │      validate_export.py（唯一裁判）   │   ← "法官"：
   │  类型转换 / 合计校验 / 问题记账 / 归档  │      负责"按什么规则记账"
   └─────────────────────────────────────┘
         │ 数据 + 问题账本
         ↓
   ┌─────────────────────────────────────┐
   │   task_review.xlsx（你填一次）        │   ← "法庭"：
   │   填「员工决定」+「是否归档」两列      │      人只做判断题
   └─────────────────────────────────────┘
         │ 你的决定（由脚本导入成 decisions.json）
         ↓
   ┌─────────────────────────────────────┐
   │  重新跑一遍 → final.xlsx + 归档原图   │   ← "判决执行"：
   │  + facts.jsonl（机器读的长表）+ 摘要   │      数据落账、照片归位
   └─────────────────────────────────────┘
```

五句话总结分工：
- **AI 负责"看"**：照片里写了什么，原样读出来，允许说"我看不清"。
  它唯一的产出物是**识别片段**——**不手写 `raw.json`**。
- **脚本层负责"搬运"**：建任务、算指纹、编号、单位换算、补必填、原子落盘、导入审核、
  导出长表、出摘要。全部是确定性代码，不靠 AI 记性，也不靠 AI 手稳。
- **裁判负责"算和判"**：类型转换、合计检查、问题登记、生成 Excel、归档。
- **人负责"拍板"**：只在真正需要业务判断的地方出手，而且**一次性集中处理**。
- **文件负责"记住"**：词典、错题本、标准答案都落在文件里，越用越准。

### 为什么要把"脚本层"单独拎出来

以前 AI 要亲手写整个 `raw.json`——里面混着任务编号、图片路径、指纹、行号、
必填字段、单位换算（`89.6%` → `0.896`）、建议文件名。这些活有三个共同点：

1. **是机器的活**，不是判断题，AI 做只是"打字"；
2. **AI 手工做容易错**，而且要等到最后跑校验才发现；
3. **错了很难查**，因为分不清是"看错了"还是"抄错了"。

现在这三类活都交给脚本，于是分工变得干净：
**AI 错了 = 看错了（进问题清单，人复核）；脚本错了 = 逻辑错误（跑自测就能抓）。**

脚本层还把两类错误**分开对待**，这是整个设计的核心：

| 错误类型 | 例子 | 处理 |
|----------|------|------|
| **格式/契约错误** | 缺 `row_role`、列名不在契约里、数值解析不出来 | **当场拒绝**（退出码 2，什么都不写），让 AI 改好再交 |
| **业务疑点** | 合计超 100%、同类词没注册、某格看不清 | **照常落盘**，记账，留到最后一次性交人复核 |

前者是"写错了"，后者是"流程设计：疑点记账、中途不打扰人"。分清楚了，
才不会出现"AI 为了通过校验，把看不清的数字猜一个填上"这种事。

## 三、技能是怎么装到各种 AI 工具里的（工具无关设计）

这套东西**不绑定某一个 AI 工具**。Codex、DSH、ZCode、Cursor、Claude、OpenCode，
只要它认识 `SKILL.md` 这种"技能文件"格式，就能用同一个技能。

### 三件东西，各就各位

```
技能源文件（唯一真源）        工作区（唯一数据源）        各家工具的技能目录
图像识别长期工程\             图像识别长期工程\           .codex\skills
  技能源文件\                    inbox\ archive\ runs\      .dsh\skills
    image-data-recognition\      golden\ schemas\ ...       .cursor\skills
        │                            ↑                      ...
        │  安装脚本一键复制           │  workspace.txt 指向它
        └───────────────────────────┴──────────────────────┘
```

- **技能源文件**放在工作区里，跟着数据一起走。改一次，重跑一次安装脚本，所有工具同步更新。
- **每家工具要装一份**，因为工具只认自己家的目录。
- **技能里不写死工作区路径**。每个技能副本里有一个 `workspace.txt`，只写一行：
  工作区在哪个目录。AI 加载技能后第一件事就是读它。

### 为什么要这么设计

| 如果…… | 会出什么问题 |
|---------|-------------|
| 把技能路径写死在 SKILL.md 里 | 换电脑、换盘符、换用户名就全废了 |
| 技能只装在一家工具里 | 想换个工具试试就得重新折腾一遍 |
| 技能和工作区分开放两个地方 | 搬家要记得搬两次，很容易漏 |
| 用脚本去猜工作区在哪 | 猜错了会静默读错文件夹——比报错更危险 |

### 找不到工作区时怎么办（自修复顺序）

技能被加载后，AI 按这个顺序找工作区：

1. 读技能目录里的 `workspace.txt`；
2. 路径有效 → 直接用；
3. 无效/缺失 → 在当前打开的项目里找 `validate_export.py`；
4. 还找不到 → 在桌面找名字含「图像识别长期工程」的文件夹；
5. 全找不到 → **直接问用户**，拿到答复后写回 `workspace.txt`。

关键点：**第 5 步是"问人"，不是"猜"**。这台系统的铁律是"不猜"，找路径也一样。

## 四、数据分五层（本系统最重要的设计）

问过自己一个问题：**万一 AI 看错了，这个错误会跑到哪里去？** 为了防止"看错的数据混进正式台账"，把数据分成了五层，物理上分开存放：

| 层 | 存在哪 | 作用 | 规矩 |
|----|--------|------|------|
| 证据层 | `runs/*/source/` 原图 + `source/names.json` 图片台账 + `runs/*/raw.json` | 记录"AI 到底看见了什么"、这批图到底是哪几张（编号与指纹） | **只读，写完永不修改**。查错全从这查。`raw.json` **只由 `tools/提交识别.py` 写** |
| 工作层 | 内存里的行数据（由**识别片段**补全而来） | 带状态（正常/待确认/阻塞）的中间数据 | 可以反复重算，**永远不会直接变成正式数据** |
| 问题层 | `runs/*/issues.json` + `decisions.json` | 今天要你判断什么、你怎么判的 | 一条问题记录"影响范围"，你一个决定自动作用到所有相关行 |
| 规则层 | `schemas/` + `aliases.json` | 每种单据长什么样、词怎么归类 | 改规则要你同意，且留痕可回滚（改版 = 新增 `_v2`，旧版永久保留） |
| 事实层 | `final.xlsx` + `runs/*/facts.jsonl` | 最终盖章的数据（一份给人看，一份给机器读） | **只包含已确认的事实**；没解决的一律不进 |

为什么这样分？举一个真实会发生的例子：
> 某天某张化验单上 DMF 那个数字糊了，AI 看不清。

如果系统只有"一份数据"，AI 很可能猜一个、或者干脆不写。猜错了没人知道。
现在这个设计下：AI 说"看不清"，这行数据**进不了事实层**，只在问题账本里躺着等你；你对照原图填上正确值，系统才重新算一遍、放它进 `final.xlsx`。
**"没确认的数据永远进不了正式数据"——这是整套系统的地基。**

> 一个容易看漏的细节：识别阶段"每交一张图就落盘一次"，靠的是
> **先写临时文件、再整体替换**（原子写）。所以断电、关机、杀掉 AI，
> 最坏情况是"这一张还没交上去"，绝不会留下半个文件把整个任务弄坏。

## 五、一次任务的完整流程

```
1. 你扔图            照片放进 inbox/（不分类、不改名）
2. 建任务（脚本）    原图复制进 runs/日期_编号/source/，逐张算"指纹"防重复，
                     写图片台账 source/names.json，写一个空的 raw.json 骨架
3. 识别（AI 看图）   AI 用 read_image 看一张 → 交一小段"识别片段"
   ├─ 脚本补全        编号、换算（89.6% → 0.896）、必填字段、单位，全部脚本算
   ├─ 格式不合格      当场退回（退出码 2，什么都不写），改好再交
   └─ 业务疑点        照常落盘，记账，留到最后一次性复核
   ├─ 老表格          直接按已注册的契约读
   └─ 新表格          先给你一份样板（一行是什么/列是什么/有没有合计），
                      你确认后才注册契约（row_unit 没答就不许写），再继续
4. 校验（裁判）      跑脚本：类型转换、合计检查、问题登记 → issues.json
5. 审核              生成 task_review.xlsx 给你；你填「员工决定」+「是否归档」两列
6. 收决定（脚本）    导入审核.py 直接读你填的单元格 → 权威的 decisions.json
                     （不再有人工誊抄这一步）
7. 收尾              你填完 → 系统重新跑一遍（全量重算）
8. 落账 + 归档       生成 final.xlsx；导出机器读的长表 facts.jsonl；
                     原图按日期改名归档，永不覆盖
9. 关闭（脚本）      收尾报告.py 从磁盘账本读数字，出一句话汇报：
                     录了几张、几行、几个问题、归档到哪
```

**关键点：进程可以被打断。** 每一步的结果都落在磁盘上，任何时候中断/关机/重启，重新跑同一条命令即可继续，之前填过的决定不会丢。

## 六、几个关键设计，以及为什么

### 1. 为什么"问题集中问一次"，而不是遇到一个问一个

一开始的设计是"发现疑问立刻弹给操作员"。问题是：一张单子有 3 处糊了、一天 20 张单子，人就变成了"审核机器"，一格格被打断，还容易在反复跳转里看漏。

现在改成：**AI 先把今天能干的活全干完，所有疑问进同一个"问题账本"；你抽出 5 分钟一次性处理。** 你在审核表里做的事只有一件——对每一行问题给出结论（选候选值、填正确值、或"按原样通过"）。**没有问题的数据默认就是对的，不需要逐个确认**（否则 200 行会看死人）。

### 2. 为什么"AI 只交片段、不写整个文件"

三个理由，按重要性排：

1. **出错面变小**：AI 要手写的东西从"整个 `raw.json`（编号、路径、指纹、行号、
   必填、换算、文件名）"缩到"这一张图上我看到了什么"。剩下的都是脚本的事，
   而脚本不会打错字、不会忘记续号、不会把 `89.6%` 换成 `0.898`。
2. **错了立刻知道**：格式错误**当场**退回（不是等到最后跑校验才发现），
   而且退回时什么都不写——不会出现"写坏了一半"的任务文件夹。
3. **分工可解释**：AI 错了就是"看错了"，脚本错了就是"逻辑错了"。
   两种错误有各自的检查手段（人复核 / 自测脚本），不会搅在一起。

### 3. 为什么"合计超 100% 一律报错，不给容差"

这不是计算机问题，是业务判断，你在方案讨论里定了调：
> 化验仪器给的数据是精确的，人工只是誊抄，抄出超过 100% 必定是抄错了。

所以系统**不设任何容差**：只要"应计入合计的组分"加起来超过 100%，立刻标红进问题清单，等你对照原图给正确值。

一个技术细节（真的会发生）：计算机算小数时会出现"100.00000000000001"这种鬼数字。本机实测 23,804 组数学上正好等于 100% 的数据，用普通小数加法有 **94 组**会被算成"超过 100%"——**全是对的化验单，却被误报成抄错**。所以脚本内部把百分比换算成整数再相加，误报归零。这是"看似小事、实则关键"的一处。

### 4. 为什么"杂"那格官方做法是留白

讨论过三种做法：自动补算（100% 减去其他组分）、报错、留白。
最终你拍板：**有值就照录，空白就留白，机器不补算。**
理由：自动补算等于"机器造了一个数据"，还标成"计算值"，将来做趋势图时你根本分不清那是化验单上写的、还是机器编的。留白虽然"少了点信息"，但**永远不会骗人**。宁缺毋假。

### 5. 为什么审核用 Excel、而"抄进 JSON"这一步交给脚本

- 你已经会用 Excel，不需要学新工具；
- 审核表支持下拉、批注、红黄标色，够用了（本机实测：下拉、批注、员工改动后程序读回，全部正常）；
- 做界面的成本远高于收益，还会引入新的维护负担。

但"把 Excel 里的字抄进 `decisions.json`"这一步**过去是 AI 用眼睛抄的**，
它是整条流水线上唯一的手工誊抄环节，也最容易错：抄错一个编号，那条决定就静默失效
（脚本只会当作"没填"）；抄错一个数值，错值直接进最终 Excel。
现在这一步由 `tools/导入审核.py` 直接读单元格完成，**且按表头名字定位列**——
有人插一列、把表头往下推一行，它照样读对。

配套定了三条防坑规则：
1. 表格里**不写任何公式**（程序读不到公式算出来的值）；
2. 编号、决定这些格子**固定为文本格式**（否则 Excel 会把 `1-4` 自动变成日期）；
3. 你的决定按"问题编号"关联，**不按行号**——你排序、筛选、甚至删掉空行，都不会让决定错位。

### 6. 为什么"归档必须是最后一步，而且绝不覆盖"

原来的设计是识别完就顺手把照片挪走。这会出问题：**万一挪完才发现这张识别错了，照片已经在归档区了**，而且如果当时有重名文件，还可能把别人的照片覆盖掉。

实测证据：
- Windows 上有个"重命名"操作遇到同名文件会**直接报错拒绝**（这正是我们要的），另一个类似操作则会**悄悄把同名文件吃掉**——所以归档只能用前者；
- 文件名里带冒号（比如有人写时间 9:30）实际会生成一个 **0 字节的空文件**，看着像照片，其实是废的——所以自动命名前必须洗掉非法字符。

现在改成：识别阶段只生成"归档计划"（准备改什么名、放哪），**你审核确认后**才统一移动；移动时逐条记录成功/失败，中断了可以只补没完成的。

### 7. 为什么用"长表"存成分数据

成分数据有两种存法：
- **宽表**：一行一个桶，每个成分占一列（IPAC、DMF、水、甲醇……几十列）；
- **长表**：一行一个"事实"（哪个桶、哪个成分、多少）。

你的业务里成分每天都在变、新成分随时出现。用宽表的话，今天多一种成分就得加一列，几个月后表会烂掉，图和公式也全要重做。
长表则**列永远不变，只是行数增加**——这恰好也是 Excel 数据透视表和 Python 最喜欢的格式。所以：**宽表给人看（核对，进 `final.xlsx`），长表给机器算（做图、统计，进 `facts.jsonl`）。**

现在长表是 `tools/导出长表.py` 直接生成的：一行一条事实，带上"来源行号"和"图上原文"，
纯文本、能直接 diff——将来数据量大了要搬进数据库，**原样导入即可，不用重新识别一遍**。

### 8. 为什么暂时不用数据库

你现在每天几张单子，Excel 完全扛得住。但结构设计已经按数据库的规矩来（一行一条事实、关键字段齐全、保留来源编号），将来数据大了要搬进数据库时，表格原样导入即可，**不用重新识别一遍**。

### 9. 为什么"方案不冻结"

这是你提的现实：公司即将全面改版所有单据（为了让一线员工好填），所以表头、单位、命名格式**全都不能提前定死**。系统用"逐表注册"应对：遇到新版式就注册一版新规则，旧规则永久保留，历史照片照样能读。

## 七、质量保障：四重防线

| 防线 | 谁来守 | 挡住什么 |
|------|--------|----------|
| 第一重 | 识别阶段的"不猜"原则 | 挡住 AI 的"合理化猜测"——看不清就明确说看不清 |
| 第二重 | **脚本层的当场校验** | 挡住"格式写错"——缺身份（`row_role`）、用了契约外的列、数值解析不了，**当场退回、什么都不写** |
| 第三重 | 裁判的确定性校验 | 挡住数学错误——合计超百、类型不对、必填缺失，全部机器判定 |
| 第四重 | 你的一次性审核 | 挡住业务语义错误——机器不知道"这张单子实际是怎么回事" |

外加三个长期机制：
- **标准答案库**（golden）：你确认过的结果单独保存、只增不改；日后改规则时用它对历史数据做回放，**确保改规则没把以前对的东西改坏**。
- **错题本**（FEEDBACK_LOG）：记录每一次人工确认过的错误，同类错误反复出现就触发"改规则"流程（需你同意），让系统越用越准。
- **两条自测命令**：`python tools/回归测试.py` 守裁判（改裁判必须全绿）；
  `python tools/新流程自测.py` 守脚本层——它在系统临时目录里跑一遍完整流程，
  **真实数据一个字节都不动**。改了 `tools/` 下的脚本，两个都要全绿。

---

## 八、明确不做的事（红线）

不做第二套视觉接口、不装本地 OCR、不做数据库/向量库、不做网页界面、不自动生成公式、不逐格提问、**不替用户编造数据**、**不把未解决的数据放进正式台账**、**不让 AI 手写数据文件**（`raw.json` 只由脚本写）。

这些不是"技术不行"，而是每一条都会增加出错的可能性和维护负担。首版把精力集中在"数据绝对不出错"这一件事上。

## 九、名词对照表（看不懂时回这里）

| 名词 | 大白话 |
|------|--------|
| 识别片段 | AI 交上来的"这张图上我看到了什么"，每张图一小段；唯一由 AI 产出的东西 |
| 图片台账（`source/names.json`） | 这批图是哪些、编号叫啥、指纹是多少；由 `建任务.py` 写 |
| raw.json | 脚本补全后的"看见的原文"（证据，永不手改）。**只由 `提交识别.py` 写** |
| issues.json | 今天需要你判断的问题清单 |
| decisions.json | 你的决定（唯一权威记录）。由 `导入审核.py` 从审核表导入 |
| final.xlsx | 最终数据（宽表，给人看；只含已确认的事实） |
| facts.jsonl | 最终数据（长表，给机器读；一行一条事实）。由 `导出长表.py` 出 |
| task_review.xlsx | 给你审核用的表（4 个页签），**派生文件**，重跑会整表重写 |
| 样板.xlsx / 样板_契约草案.json | 新表型第一次做给你看的样例；草案是注册表型的输入 |
| 脚本层（tools/） | 干"机器的活"的那一层：建任务、提交识别、注册表型、导入审核、导出长表、收尾报告 |
| schemas/ | 每种单据的识别规则（长什么样、有哪些列） |
| aliases.json | 成分词的归类字典（水类、杂类等） |
| golden/ | 标准答案库（你确认过的结果） |
| 事实层 | 最终盖章的数据，做图表只从这里取数 |

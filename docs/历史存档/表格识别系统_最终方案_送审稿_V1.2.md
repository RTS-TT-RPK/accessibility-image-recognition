## 1. 背景、环境与目标

### 1.1 实际环境（已确认）
- 运行载体：Codex（桌面），当前会话已接入视觉模型（文中称 DSV4），可直接看用户上传的图片。
- 本机已装：Python 3.12.10、openpyxl 3.1.5、pandas 3.0.3（无需新装依赖）。
- 明确不引入：第二套视觉 API、vision_extract.py、本地 OCR 引擎、SQLite、向量库、DSPy/TextGrad、GUI、微服务、Docker。
- 数据无需保密，可直接使用公共云视觉能力。
- 载体策略（V1.2 补充，用户已确认）：**当前用 Excel 承载，并为将来迁移数据库预留结构**（见 4.1 末段）——首版不引入数据库，但数据模型按关系型事实表设计。

### 1.2 业务对象（来自用户真实单据）
- 表型数量：现有约 7~8 种版式（全公司业务单据类型大概率不超过 10 类），新增频率不高，偶尔调整。
- **重要前提（用户 2026-09-10）**：公司正在重新设计全部业务单据，以适配一线员工的填写水平并便于后续数字化。故本项目面对的版式是"当前可用 + 持续改版"状态：**表头、单位、命名格式一律不提前冻结**；改版即视为同一业务表的新版本，重新注册后生效，旧版 schema 保留以读取历史照片。
- 库存日报：一张图含两个逻辑表。上半部分"库存明细"（每行=储存位置+物料）；下半部分"现场库区原料明细"（每行=现场存储分类）。图底部存在合计/汇总行。
- 来料化验分析：每批来料若干桶，通常每行=一桶/一个样品；**同一批料可能由多张照片组成**（分图拍摄），需按批次归组。
- 成分明细形态：图中每个成分名称与其百分比各自独立成格（如 甲醇 | 30% | 乙醇 | 40% | IPAC | 10% | 高沸物 | 5% | 杂 | 15% | 含水量 | 5%），可逐格取数；含水量属独立指标（与 PH 类似），不与组分合计混淆。
- 数值特征：图上数值均明示（如库存、变动量），**无需正负号约定或不等号特殊语义**；识别后计算交给 Excel 函数/Python。
- 组分逻辑：非含水量组分之和不得超过 100%，S>100% 即报错且无容差（见 4.4）；不足 100% 时，仅当图上明确写了杂且该格无数值才补"杂分（计算）"，未写杂则不补不提示；含水量等易歧义词的归类由 4.5 校验词典动态注册确定。

### 1.3 目标优先级
结构正确 > 业务语义正确 > 可计算 > 视觉原样还原。
- 普通图片一次识别直接产出 Excel；拿不准时主动问；关键处宁可多问一次。
- 数据详实可查、可追溯；支持 Excel 函数/透视表/Python 分类计算与会议图表。
- 越用越准，且进化不破坏已有能力。

## 2. 总体架构
Codex+视觉模型（看与理解、编排、读写文件）+ 本地 Python 校验器（确定性校验与 Excel 生成）+ Schema 契约（数据定义，逐表注册、不冻结）+ 记忆文件（错题/别名/标准答案）+ Git（回滚保险）。

一句话：视觉大脑负责"看到什么"，业务规则负责"按什么结构记"，Python 负责"裁判与落盘"，人负责"抽查确认"。

## 3. 目录结构（冻结版；当前落地于本机工作目录，示例中记为 <工作目录>/）
<工作目录>/
- AGENTS.md：唯一行为手册（Codex 每次执行依据；AI 可改，但须走进化流程）
- schemas/：版式契约库。**初始为空（只放 README 与示例骨架）**；每类新表型经提案确认后新增一个 JSON；修改既有列定义须人工同意
- validate_export.py：唯一代码：JSON 清理→通用不变量→类型转换→组分合计校验→三态判定→写 xlsx（内部 validate()/export()/main()）。AI 永不自动修改，只允许人改。通用不变量写在这里，不另设 generic schema 文件

## 4. 数据模型（核心）

### 4.1 通用"事实结构"（每个结构=一个 Sheet；随注册模板细化）
结构 A：明细宽表（例：库存明细）——每行=某天某对象（储存位置+物料 / 桶+样品）：
- 日期（真日期，取图标题一次填到每行）、位置/区域、物料名称、来源/厂商（有则填）
- 各业务数值列（如 变动量_吨、库存_吨）：**按图内明示数值原样录入**，不做符号解释
- 成分明细_原文（原样保存，一字不改）
- row_role：data / summary / header / note
- 其余列由该模板的 schema 决定（不冻结全集）

结构 B：成分明细（长表）——每行=一个成分含量事实，是趋势图与分类计算的数据源：
- 日期、来源类型（inventory/incoming）、位置/区域、批次号、桶号（有则填，无则空，禁止为填字段而猜）
- 物料名称（必填）、厂商/来源
- 成分原名：永远保留模型看到的原始名称
- 成分标准名：仅当校验词典（4.5）已有用户确认映射时填写；否则留空
- name_status：confirmed / pending（未确认时标准名留空并标 pending；禁止把"待确认"写入名称字段，防止按标准名筛选时漏数据）
- 成分类别 category：composition（计入合计的组分，如甲醇/乙醇/IPAC/高沸物/杂）/ water（含水量类，独立指标，不计入合计）/ quality（PH 等无%指标）/ other（具体词的归类由 4.5 校验词典注册决定，不在代码中硬编码）
- count_in_total：是否计入组分合计（composition=true；water/quality=false）
- 原始值：模型输出原文（如 30%、11.6）
- 数值：Python 按 schema/单位转换后的数值；无法确定则空并触发 REVIEW
- 单位：% / pH / 吨等（来自 schema 列定义或行上下文，Python 校验，不靠模型猜）
- data_source：ocr（图上原样） / derived（Python 计算生成，如杂分）
- source_run_id / source_row_id：本条事实的来源 run 与来源行号（可回溯到 runs/YYYYMMDD_NNN/raw.json 与原图）

结构 C：来料/批次明细（宽表）——每行=一桶/一样品；同一批次多张照片的行合并到同一批次下，行内记录来源照片编号。

**数据库预留（V1.2 补充，用户已确认）**：首版不引入数据库，但全部事实表按数据库思想设计——一条事实一行、字段名与列序稳定、编号类文本、日期为真日期、不合并单元格、保留 source_run_id / source_row_id / batch_id / container_id 等关联键、derived 行用 data_source 标记、summary/header/note 行永不入账。将来数据量增大时，这些 Sheet 可原样导入 SQLite/数据库（字段与行语义不变），**无需重新识别、无需改模型**；Excel 始终是交付与查看格式。

汇总行规则：合计/汇总行允许出现在"给人看的日报/核对视图"并标 row_role=summary；**任何 summary/header/note 行永不进入长期事实台账**，防止 SUM/透视表重复统计。row_role 由视觉模型判断，Python 只分流不猜。

### 4.2 单图到 Sheet 的映射规则
- 先判断业务对象（几张逻辑表、每表的一行是什么），再判断列。
- 同一记录集合（样品信息+检测结果描述同一对象）→ 合并成一张宽表的一行；不同记录集合（库存明细 vs 现场库区明细）→ 不同 Sheet。
- 多个样品/桶重复块 → 一行一桶/一样品，关键字段（批次、日期、位置）重复到每一行，保证每行自洽。
- 多级表头 → 语义扁平化为唯一稳定字段名（如 理化_水分），schema 记录 header_path 溯源；不输出 rowspan/colspan。
- 结构存在两种合理解释 → 在提取之前问用户一次。

### 4.3 单元格语义约定
- "" = 原图空白；"N/A" = 原图明确写 N/A；看不清 = 必须进 uncertain 列表；禁止静默猜值。
- 模型只输出"看见的原文"；一切类型转换在 Python 内完成，锚点是 schema 的 type/unit。
- 带不等号/范围等特殊写法的单元格（如有）：按文本原样保留并触发 REVIEW，不引入运算符语义结构。

### 4.4 组分合计校验与杂分补齐（Python 确定性规则，核心业务校验；V1.2 定稿）
对每个“来源行”（某图某物料的成分集合）：
1. 取该行所有 count_in_total=true 的百分比项求和 S（含水量、PH 等不计入）。S 用原始精度计算，不做人为取整。
2. **S > 100% → 硬报错（BLOCK，无容差）**：分析仪器给出的结果精确，人工誊抄的就是仪器数据，超过 100% 必定是誊抄或识别错误。该行不落账、不出最终 Excel；Codex 对照原图定向复看相关数字格最多 1 次（附候选值，如 0.8 与 8.8 之别）；仍不定 → 带完整数据清单停下，由操作者对照原图口述正确值，AI 修正 raw.json 后重跑校验（见 6.3）。不设近似放行。
3. **S < 100% → 默认不补、不报错、正常通过**，摘要区显示“合计 xx.x%”供扫看，不产生任何状态。
4. 唯一例外：图上**明确写了“杂”（或注册词典确认的杂类词）但该格没有数值** → Python 生成一行派生数据：成分名=“杂分（计算）”、数值=100%−S、data_source=derived，核对视图黄格标注“图片未给数，系统补算”。
5. 图上写了“杂”且有数值 → 照原样录入，不做二次补写；此时校验“其余组分 S + 杂项数值”≤100%，>100% 按第 2 条报错。
6. 哪些词算“杂类”、哪些词算“含水量类”，不在代码中硬编码：由 4.5 校验词典注册决定；未注册的词按普通成分处理并在摘要中标 pending。
7. 该规则属 validate_export.py 的不可变逻辑（AI 永不自动修改）；derived 行与 ocr 行严格区分，台账/图表如需“只含原图数据”可按 data_source 过滤。
8. 特殊表型后门：若某类仪器单据本身取整打印（如只到整数位）导致系统性超差，只能在**该表型注册时**单独登记放宽规则，不改全局规则（默认无任何放宽）。

### 4.5 歧义词动态注册（V1.2 新增：一切“可能同义/特殊”的词都走这里）
原则：任何容易歧义的词（同义改写、是否计入合计、是否触发补算）一律不预设、不由 AI 猜测，全部走“AI 提案 → 操作者拍板 → 写入校验词典 → 固定执行”。
- 触发时机：① 新表型注册（6.5）时一次性列出该表全部歧义词；② 已注册表型首次出现从未见过的词（标 pending）。
- 提案示例（AI 一次问清，不逐格提问）：
  - 含水量/水分/水/水份 → 归 water 类，独立指标，不计入合计（首版默认建议，需操作者确认）；
  - 杂/杂质/杂分 → 归 miscellaneous 类，触发 4.4 的补算规则；
  - 高沸物/其他/残渣 → 是否算普通组分或杂类，由操作者拍板。
- 落点：aliases.json（成分名映射）+ 各 schema 的 category 定义；每次更新 git commit，可回滚。
- 未注册词的行为：成分原名照留、标准名留空、name_status=pending，不参与合计与补算；交付摘要一次列出全部 pending 词，问清后再注册。
- 已注册词的行为：固定执行、不再询问。发现注册错误 → 走第 9 节规则修订流程（需操作者同意）。
- 词典只增不改语义：修改既有词义必须人工确认并记 FEEDBACK_LOG。

## 5. Schema 与类型系统

### 5.1 每列定义字段
name / aliases（同义列名）/ type / unit / category（成分行用）/ count_in_total（成分行用）/ export_type / excel_format / date_formats / required / allow_blank / notes。
示例（示意，非冻结）：{"name":"甲醇","type":"percent","unit":"%","category":"composition","count_in_total":true,"export_type":"numeric","excel_format":"0.0%"}；
{"name":"含水量","type":"percent","unit":"%","category":"water","count_in_total":false,"export_type":"numeric","excel_format":"0.0%"}；
{"name":"PH","type":"decimal","category":"quality","export_type":"numeric","excel_format":"0.0"}；
{"name":"库存_吨","type":"decimal","unit":"吨","export_type":"numeric","excel_format":"0.00"}；
{"name":"批号","type":"identifier","export_type":"text"}；
{"name":"日期","type":"date","date_formats":["YYYY/M/D","YYYY.M.D"],"export_type":"date"}
- 单位不预设全集：每个模板的 schema 自带其单位；跨模板同指标单位不一致时，按规范化名提示 pending（4.5 注册后生效），不自动折算。

### 5.2 类型转换红线
- percent：12.5% 转 0.125（Excel 显示 12.5%）；0.6% 转 0.006；60% 转 0.6。存分数而非百分数本身。
- 裸数字出现在 unit=% 列：按列定义转换；无依据不转并 REVIEW。
- date：仅白名单格式且上下文明确才转真日期；6.4、03/04、2026-01、1-4 一律不自动转日期（identifier/文本或 REVIEW）。
- identifier/编号/位置名：永远文本，写入前设 Excel 单元格格式 @；禁止撇号 hack。
- 转换失败或模式不符 → REVIEW，绝不猜测。

### 5.3 双层契约
- 通用不变量（任何图都生效，写在 validate_export.py）：JSON 可解析、fence 清理、行键一致、无全空行、结构断裂检测、identifier 不被日期化、类型与必填检查、组分合计校验。
- 版式契约（schemas/*.json，逐表注册）：某模板的 Sheet 名、列定义、列顺序、别名、category/count_in_total。
- TEMP（陌生模板）流程：见 6.5。

## 6. 一次任务的完整流程与产物

### 6.1 输入、内容自动整理与批次归组（V1.2 重写）
- 操作者只做一件事：把照片扔进 inbox/（可按日期建子夹，如 inbox/2026-09-10/，仅为方便本人查找）。**不要求预先按表类分类，也不要求逐张改名。**
- 三种来源均可：聊天贴图 / 本地路径 / inbox 目录。统一生成 raw.json，Python 不关心来源。
- AI 逐图读取图内自带的日期、版式特征与批次号，据此生成业务名并归档：
  - 业务名格式**暂不冻结**（用户明确：业务单据正在改版，定稿后再定命名顺序）。机制固定、格式待定：AI 从图内读取日期/表种/批次拼出可读名，当前先用临时规则 `日期_表种_第几张`（如 `2026-09-10_库存日报_第1张.jpg`）作为档案索引；**格式即使将来更换，也只影响文件名，不影响数据与追溯**（映射表单独保存）。
  - 归档位置：archive/YYYY-MM-DD/（必要时再按版式或批次分一层），核对通过后由 AI 移入。
- **三条安全线（必须遵守）**：
  1) 原名永不被覆盖：run 内保存“原文件名 ↔ 业务名”映射（source/names.json），任何改名始终可逆；
  2) 文件夹只是索引、不是证据：类别/日期/批次一律以 Excel 与 raw.json 记录为准，归档夹分错可随时重排，不影响台账；
  3) 读不出来就不猜：日期或批次置信度低、同批出现两个日期等冲突 → 移入待确认区（pending/），交付摘要中问一次，禁止编造名字。
- 多图同批：AI 依据图内批次号自动归组（图内无批次号或冲突时才请操作者说明一次）。每张图独立 run（共享 batch_id），台账按 batch_id + 桶号合并，行内记录来源照片编号。


### 6.2 识别顺序（写死在 AGENTS.md）
1) 图片可读性预检（模糊/倾斜/过暗 → 请用户重拍）；
2) 结构先行：判断版式类别（单表/多级表头/组合表/重复样品块）与业务对象；
3) 选 schema：已知模板用契约；未知走 TEMP（6.5）；
4) 按 schema 输出"原文 JSON"（含 sheets、uncertain、meta），保存 raw.json。

### 6.3 三态判定（Python 为唯一裁判）
- PASS：JSON 可解析+schema 确定+字段/类型/结构/组分合计全绿 → 直接出 Excel。
- REVIEW：结构成立但有局部疑点（含数字格疑似看错与合计异常）→ Codex 对照原图定向复看最多 1 次（带候选值）；仍不定 → 带候选值问用户；复看后更新并复检。
- BLOCK：结构无法确定/关键列整列缺失/JSON 无法恢复；或组分合计 S>100%（无容差）→ 复看最多 1 次仍不定则不落账、不出最终 Excel，请操作者口述正确值，AI 修正 raw.json 后重跑。
- 结构级歧义在提取前先问；全程不使用模型自报 confidence。

### 6.4 每任务产物（runs/YYYYMMDD_NNN/）
- raw.json：模型原文输出+uncertain+meta（processing_mode: known_schema/temporary_schema、source_type、contract_version: 1.0、batch_id 若有）
- validation.json：status、template、sheet_count、各表 row_count、uncertain_count、review_count、derived_count、sum_check（组分合计校验结果）、user_corrected、root_cause
- final.xlsx：数据工作簿，每个结构一个 Sheet（纯数据无合计行；identifier 文本；percent/date/数值真实类型；derived 行以"（计算）"标注）
- review.xlsx：核对工作簿（见第 7 节）
- source/：原图副本（来自 inbox/本地路径时复制；聊天贴图以对话原图为准）
- 聊天交付一行摘要：模板、各表行数、复核次数、状态、文件路径。BLOCK 交付原因清单。

### 6.5 新表型注册流程（固定为一级流程）
1. 遇到 schemas/ 中不存在的版式 → 先按 TEMP 识别并产出**录入方案提案**（人话版草案）：拆哪几张表、每表哪些列、每列单位与类型、示例行、row_role 与合计处理、组分合计规则是否适用，以及该表全部歧义词的分组提案（如 含水量/水分/水 的归类、哪些词算杂，见 4.5）。
2. 操作者直接修订草案（改列名/增删列/改单位），确认后注册为正式 schema（git commit）。
3. 该表型后续照片直接按 schema 执行，不再提问；识别仍按 6.3 三态校验。
4. **改版处理（与用户"单据即将全面改版"的现实对应）**：同一业务表改版 = 新版本 schema（如 `incoming_analysis_v2.json`），旧版文件永久保留；识别时按版式指纹选版本，历史照片仍可正确解析；改版不改数据模型（事实表字段稳定，只增不改语义）。
5. 提案不以"一问一答"方式进行：一次性给出可修订的完整草案清单，降低操作者成本。

### 6.6 单据改版期间的协作（V1.2 新增：反向输出"便于识别"的版式建议）
公司改版纸质/电子单据时，本系统可反向提供"更容易识别、更少歧义"的版式建议，降低一线填写难度与后期录入成本。建议清单（供设计新表样时参考，非强制）：
- 一个格只放一个值：成分名与百分比各自独立成格（如 甲醇 | 30%），不要写成一格长文本。
- 日期统一为固定格式（如 2026-09-10），不要用 6.4、1-4 这类易被误读为日期的写法。
- 批次号、位置、物料名放在固定列且每行重复（不要只在表头写一次），便于逐行自洽与台账合并。
- 一张纸尽量只放一张逻辑表；若必须放两张（如库存日报），用明确的表头分隔。
- 编号/批号类字段避免纯数字短格式（如 1-4），优先带字母前缀（如 批A001）。
- 需要计算的数值（合计、差量）可由系统/Excel 生成，纸上不必再印，减少誊抄错误。
- 写完数值后通读一遍"非含水量组分合计"是否可能超过 100%（超百必为误记，见 4.4）。
以上建议随实际识别问题持续更新到 FEEDBACK_LOG 与本节。

## 7. 快速人工对照（用户明确要求的功能）
每次任务自动产出 review.xlsx，含：
1) 对照原图 Sheet：按图片原样排布的文字还原表（含表头、合计行，灰底标注"展示用，不进账本"）。
2) 标记分级：黄格=AI 拿不准的格子或系统补算的杂分（附候选值/补算说明）；红格=组分合计 S>100% 的超差格（该表 BLOCK，需对照原图口述正确值）。人核对时先看红格、再看黄格。
3) 录入摘要区：模板、几张表、各行数、可疑格数、derived 行数（如杂分补齐）、是否有"图上有字但未归类"内容、与上一张同版式图行数差异提示、各表非含水组分合计值（供扫看；未写杂时不足 100% 不作为错误）、待确认词（pending）清单。

真人核对三步法：1) 数行数是否一致（防漏行/漏列）；2) 扫每行日期+位置+名称是否对位；3) 只看标记格：红格优先（超差必改），再看黄格确认候选值与系统补算项。
确认"对"→ 数据才进入 golden；说"错"→ 指出行/列/正确值，AI 当场改正并记错题。

## 8. Golden、长期台账与阶段门控

### 8.1 Golden
- 用户确认正确后当场归档：原图+expected.json（人工确认后的最终结果，与 final.xlsx 一致；derived 行含计算来源标注）+metadata.json（源 run id、schema 版本、日期、是否修正过）。
- 只追加；AI 永不修改既有条目；人发现旧答案错误 → 发布人工修订版 v2（新条目），不覆盖旧条目。

### 8.2 长期台账晚点开
- 第一版 append_to_master: false，只做"每日 Excel+golden"。
- 稳定运行 20~30 张后置 true，再自动累积台账（明细宽表+成分长表，按注册模板）。
- 关闭期间数据不丢：账本可从 golden 重建，无需重跑识别。
- 台账只含 row_role=data 的行；同一批次多图的行按 batch_id 合并，重复照片/重复桶的判重规则在开启前与用户确认。

## 9. 自进化与规则管理
- 反馈分级：偶发错误只记 FEEDBACK_LOG；同类错误反复出现且属规则性问题（或用户明确要求）→ 进化提案 → 用户同意 → 改允许文件 → 小样本 golden 回归（每受影响模板 1~2 张）→ 通过 → git commit；失败 → git restore。
- FEEDBACK_LOG 条目：FB-ID、affected schema、字段、模型输出、人工正确答案、occurrence、错误类型、处理方式、状态；根因分类：视觉误读/结构遗漏/类型与单位/表头映射/需求差异（用户偏好≠错误，只记录不改规则）。
- 新规则必须注明 replaces/related_to；冲突或重复时人工清理，不用固定条数触发。
- 成分规范化红线：原名永远保留；标准名仅允许已确认映射；新名称留空并标 name_status=pending，禁止自动合并；同类词的归类一律走 4.5 动态注册（AI 提案→用户拍板→写词典→commit）。
- 不可修改（AI 永不自动动）：validate_export.py、tests/（若有）、既有 golden expected.json、既有 schema 核心列定义。可修改：新增 schema（经 6.5 提案）、规则文本、FEEDBACK_LOG、aliases（经用户确认）。
- 每次纠错、schema 注册与进化后 commit。

## 10. Excel 工程规则（openpyxl）
- 类型由 schema 决定，不让 Excel 猜：identifier/文本列写前设 @；percent 存分数+0.0%；数字存数值+格式；日期存真日期。
- 数据表不创建合并单元格。
- 将来自动生成公式（阶段 2）：遵守函数白名单（2007 时代函数、_xlfn 前缀规则、禁 XLOOKUP/SORT/FILTER 等）；写入后必须重算校验——实现工具在搭建时确认（本机 Excel COM 或现有可用重算工具任一），"写出公式≠公式正确"；若两者都不可用，则阶段 2 不自动写公式，改为交付不带公式的数据表。
- 借鉴 Anthropic XLSX Skill 工程思想（其仓库 Proprietary 许可，只参考不复制）。

## 11. 图表与汇报路线（Excel 还是 Python 的答案 + 软件兼容性）
- 数据先按标准结构落盘，Excel 函数/透视表与 Python 读同一份数据，切换成本为零。
- 阶段 1（日常）：Excel 原生透视表+图表（趋势折线、库存柱状、桶间对比），需要会一点透视表。
- 阶段 2（固定周/月报重复出现 2~3 次、需要箱线图等复杂图、或数据量大）：让 Codex 写报告工具（pandas/matplotlib/python-pptx），一句话生成报告甚至 PPT；用户无需会 Python。
- 红线：图表数字一律来自事实台账（无合计行、derived 行按需过滤），避免重复统计。
- 软件兼容性：产物为标准 .xlsx；不使用 VBA/宏；公式只使用 Excel/WPS 通用基础函数；图表用常用类型。WPS 与 Excel 在高级函数（XLOOKUP/SORT/FILTER 等）、新式图表、宏支持上存在差异（WPS 个人版不支持宏、部分新函数支持较晚），日常数据文件两者均可正常打开。**用户主用软件已确认（2026-09-10）：Office Excel（微软 Excel）**；产物继续保持 WPS 兼容底线（不用宏/VBA、不用新版专属函数），换机器或换 WPS 打开也不坏。

## 16. 遗留问题（需用户拍板；评审者请勿替用户决定业务语义）
已拍板（V1.2 定稿，不再讨论）：
- 组分合计：S>100% 一律报错（无容差）；S<100% 未写杂 = 不补不提示；写了杂且无数值 = 补算并标 derived；写了杂且有值 = 照录，且 S+杂>100% 仍报错。
- 易歧义词（含水量/水分/水、杂/杂质/杂分……）：不预设，全部走 4.5 动态注册。
- 图片输入：操作者只扔 inbox/，不预分类、不逐张改名；AI 按图内日期/版式/批次自动命名并归档（安全线见 6.1）。
- 多图同批：AI 依据图内批次号自动归组；无批次号或冲突时问操作者一次。
- 原图与映射：核对通过后移入 archive/ 保留、不删除；原名↔业务名映射长期保留。

## 一、结论

骨架设计是对的（确定性校验、整数合计、稳定编号、问题账本、幂等归档），
**但有三类问题在真实使用中会造成实际损失**：

1. **交付数据被污染**（人工决定变成假列）
2. **脚本说的话与产物不符**（打印"不会进入最终 Excel"，实际进了）
3. **对畸形输入几乎无防御**（模型幻觉出 `null` 就 traceback）

这三条都**不报错、不告警**，属最危险的一类。

## 二、你批准的那项修复（已上线）

### 新增 `VALUE_MISMATCH` 校验：`raw_value` ↔ `value` 必须自洽

**改了三处**：
1. `ITYPE_SHORT` 增加 `"VALUE_MISMATCH": "VAL"`（编号前缀）
2. 新增 `decimal_to_units()` / `fmt_units()` 两个函数（把"换算后小数"转成与 `parse_percent` 同一刻度的 0.01% 整数）
3. `build_issues` 的成分循环最前面插入一致性检查

**核心逻辑**：`parse_percent(raw_value)` 与 `decimal_to_units(value)` 必须相等，
不等就记 `severe` 进问题清单，该行不落账，交人判断。

**实测证据**：

| 用例 | 结果 |
|------|------|
| 回归 `runs/20260910_001` | 仍 **0 条问题**（无新的误报）|
| 回归 `runs/20260910_002` | 仍 **4 条问题**（1 严重/2 需确认/1 提示，与改前一致）|
| 构造 `DMF: raw_value="8%" / value="0.8"` | 报 **`[severe] VALUE_MISMATCH 原文与换算值不一致：DMF 原文「8%」=8.00%，换算值「0.8」=80.00%`**，该行被阻塞 |
| 幂等性 | 连跑两次，编号恒为 `ISS-VAL-R002-DMF` |
| 闭环 | 人工填 `DMF=8%` 后重跑 → 落账 `numeric_value=0.08 / raw_value=8%`，问题归零 |

**未覆盖的情况（重要）**：本校验要求**两个字段都存在**才比对。
若模型**只给了 `value` 没给 `raw_value`**，则不触发——而那种情况会造成 100 倍静默错算（见 M4）。

## 三、新发现的漏洞（均已实机复现）

### 🔴 高危

#### H1. 人工决定被写进 `row["fields"]`，最终 Excel 多出假列

- **位置**：`apply_decisions`，`row["fields"][k] = v`（无条件执行）
- **现象**：每条人工决定的键（成分名/字段名）都会变成一个**新字段**。
  实测 `runs/20260910_001`（决定为 `DMF=0`、`乙酸=0.5%`）跑完后，`final.xlsx` 的
  「明细数据」表头变成：

  ```
  行号 | 工作表 | 状态 | DMF | 乙酸 | 位置 | 批次 | 日期 | 桶号 | 物料
                        ^^^^^  ^^^^^  ← 凭空多出来的两列
  ```

- **后果**：**静默**。本次跑完提示"问题 0 条 / 任务完成"，但交付的 Excel 里
  混进了 `DMF`、`乙酸` 两个本不存在的列（成分名被当成了字段名）。
  这是**交付物层面的数据污染**，且下游看不出来。
- **建议**：只在"该键确实是本行的字段"或"问题类型属于字段类
  （`MISSING_REQUIRED_FIELD` / `DATE_AMBIGUITY`）"时才写 `fields`。

#### H2. 未解决的行，成分照样进了「成分事实」页

- **位置**：`collect_rows` —— `facts.append(...)` 不受 `status` 约束
- **现象**：实测 `runs/20260910_002`，脚本打印
  `数据行：4 行；其中未解决：3 行（不会进入最终 Excel）`，
  但同一份 `final.xlsx`：

  ```
  明细数据：   R001 ok | R002 blocked | R003 blocked | R004 blocked
  成分事实：   R001 -> IPAC=0.995
               R002 -> 甲醇=0.999, 杂=0.005     ← blocked 行
               R003 -> IPAC=0.896               ← blocked 行
  成分事实表头有没有 status 列: False
  ```

- **后果**：**静默，且与脚本自己的输出自相矛盾**。直接违反红线
  "未解决的数据行不得进入最终 Excel"。任何按「成分事实」页做汇总的下游，
  都会把超百/看不清/未注册词的值当成已确认数据，**没有任何可检测的痕迹**。
- **建议**：`blocked` 行不进 `facts`；或给 `facts` 加 `status` 列并强制下游过滤。
  （前者更符合现有红线，推荐前者。）

#### H3. 归档不做路径包含性校验，能把文件搬出工作区

- **位置**：`build_archive_plan`（用 `image["file"]` 原样，`os.path.isabs` 时不加前缀）
  + `execute_archive`（`target_dir` 直接取自人工决定）
- **现象**：实测两次，**都真实移动了文件**：

  | 测试 | 输入 | 结果 |
  |------|------|------|
  | ① 来源逃逸 | `raw.json` 里 `file` 指向 `%TEMP%\victim_outside\重要数据_不该被搬走.txt` | 该文件**被搬进** `archive\2026-09-10\搬过来的.jpg`，原位置消失 |
  | ② 目标逃逸 | `decisions.json` 里 `target_dir` = `%TEMP%\ESCAPED_ARCHIVE` | 原图**被搬到** `C:\...\ESCAPED_ARCHIVE\ok.jpg`，工作区内 `source\a.jpg` 消失 |

- **后果**：`raw.json` 是**大模型生成**的，一个幻觉出来的绝对路径就会导致
  **把工作区之外的文件搬走**。目标逃逸则破坏 `archive/` 的完整性。
  非静默（会打印"成功"），但方向和后果都错。
- **建议**：`source` 与 `target_dir` 都做 `os.path.realpath` 前缀校验
  （`source` 必须位于 `<root>/runs/.../source/` 下，`target_dir` 必须位于 `<root>/archive/` 下），
  越界即拒绝并在计划里记原因。

#### H4. 畸形输入直接 traceback（模型幻觉一个 `null` 就崩）

- **位置**：`collect_rows`、`build_issues`
- **现象**（实测，退出码均为 1）：

  | 输入 | 结果 |
  |------|------|
  | `components: null` | `collect_rows` → `TypeError: 'NoneType' object is not iterable`（第 548 行）|
  | `fields: null` | `build_issues` → `AttributeError: 'NoneType' object has no attribute 'get'`（第 327 行）|
  | `images: []`（无图）| `write_review` → `ValueError: 1 must be greater than 2`（`E2:E1` 空区间）|

- **后果**：任务中断，且**半落盘**——`issues.json` 可能已刷新、`final.xlsx` 已写出、
  但 `task_review.xlsx` 没生成，状态不一致。
  注意 `build_issues` 里 `components: null` **不会**崩（有 `or []` 兜底），
  崩的是 `collect_rows`；两者防御不一致。
- **建议**：入口统一规范化（`fields`/`components`/`uncertain`/`required_fields`
  强制为 dict/list），坏行转成 issue 而不是抛异常。

#### H5. `images` 为空时 `task_review.xlsx` 无法生成

- **位置**：`write_review` 的 `dv2.add("E2:E%d" % (len(plan) + 1))` —— **没有 `if plan:` 保护**
- **现象**：`images: []` → `plan == []` → `E2:E1` → `ValueError: 1 must be greater than 2`
- **注**：`issues` 为空的那半边**有** `if issues:` 保护，是安全的（见第五节纠正）。

#### H6. `date_text` 未清洗就拼进归档目录

- **位置**：`build_archive_plan`，`target_dir = os.path.join(archive_root, date_part)`
  —— 文件名走了 `sanitize_name`，**目录名没走**
- **现象**：实测 `date_text="2026/09/10"` → 生成 **嵌套目录** `archive\2026/09/10`；
  `date_text="2026-09-10 上午"` → 目录名带空格和中文，
  破坏文档约定的 `archive/YYYY-MM-DD/` 结构。
  若模型把日期读成 `2026:09:10`，Windows 非法字符会导致建档失败。
- **建议**：`date_text` 走同一套清洗，并校验成 `YYYY-MM-DD` 形状，不合规即进问题清单。

### 🟡 中危

#### M1. 用户在 `aliases.json` 里注册的水类/杂类词**完全不生效**

- **位置**：`load_aliases` 产出的键名是中文（`水类`/`杂类`），
  但 `build_issues` 只认 `kind == "water"` / `"misc"`；
  且 `collect_rows` 用的是**硬编码 `DEFAULT_ALIASES`**，根本不读 `aliases.json`
- **现象**：实测把「残水」注册进 `水类`，成分给 `IPAC 96% + 残水 5%`：

  ```
  报 [severe] COMPONENT_SUM_OVER_100 | 除水组分合计 101.00%，超过 100%
  ```

  —— 说明「残水」被**当成普通组分计入了合计**（正确应为 96%，不报）。
- **后果**：**静默**。用户按词典说明加词，以为生效了，实际毫无作用；
  未归类的同类词（含水率/游离水/残渣）会被计入合计，产生**假严重问题**，
  把本该正常的数据行拉进"未解决"。而且 `aliases.json` 里 `_已确认_水类` 开头的键
  被 `key.startswith("_")` 跳过，真正生效的 `水类`/`杂类` 是**空数组** ——
  同一份文件里两处列着同样的词，一处是摆设。
- **建议**：明确"生效词表的唯一来源"，把中文键映射到 `water`/`misc`；
  `collect_rows` 改用同一份已加载词表。

#### M2. `row_role` 缺失/非法时被当成 data 行

- **位置**：`if row.get("row_role") and row["row_role"] != "data": continue`
- **现象**：实测一个**故意不写 `row_role` 的"合计"行**：

  ```
  明细数据：R002 | 来料分析 | ok | 2026-09-10 | 合计
  ```

  —— 合计行以 **status=ok** 落进了明细数据。
- **后果**：**静默**。直接违反红线"表头、合计、备注行永不进事实表"。
  反向也一样：`row_role` 写成 `"total"` 这类非法值时，该行**整个消失**，
  既不进事实表也不报问题。
- **建议**：`row_role` 做枚举校验，缺失或非法即进问题清单（`ROW_ROLE_INVALID`），
  不要默认成 data。

#### M3. 水组分被**完全排除**在事实表之外（不只是不计入合计）

- **位置**：`collect_rows`，`if kind == "water": continue` 直接跳过、不入 `facts`
- **现象**：实测 `runs/20260910_001` 的成分事实页只有 `IPAC / DMF / 杂`，
  **没有「水」那一格**（raw.json 里明确有 `水 0.1%`）。
- **后果**：交付的 Excel 里，**含水量数据彻底丢失**。
  "不计入合计"与"不进事实表"是两件事，代码把它们混为一谈了。
- **建议**：**这是业务口径问题，须你来定** ——
  水含量要不要出现在最终 Excel？（我倾向：要，它是有用的业务数据。）

#### M4. `raw_value` 缺失时按 `value` 回退，导致 100 倍静默错算

- **位置**：合计用 `raw = comp.get("raw_value", comp.get("value"))`，
  而 `parse_percent` 把**裸数字一律当百分数**
- **现象**（实测数值）：同一串 `"0.896"`

  | 函数 | 结果 | 含义 |
  |------|------|------|
  | `parse_percent("0.896")`（合计用） | `90` | **0.90%** |
  | `decimal_to_units("0.896")`（正确刻度） | `8960` | **89.60%** |

  即模型漏给 `raw_value` 时，本意 89.6% 的 `value="0.896"` 会被**当成 0.90% 计入合计**（差约 100 倍）。
- **后果**：**静默**。合计偏低 → 真实超 100% 的行拿不到 `COMPONENT_SUM_OVER_100`。
- **注**：我新加的 `VALUE_MISMATCH` **覆盖不到这种情况**（要求两边都在）。
- **建议**：合计**只认 `raw_value`**；`raw_value` 缺失时记 `TYPE_AMBIGUITY`，不要回退换算。

#### M5. 解析失败的组分被排除出合计，且"通过"后即被放行

- **位置**：`parse_percent` 返回 None → 记一条 `TYPE_AMBIGUITY`(warn) 后 `continue`
- **现象**：`"1e-05"`（科学计数法）、`"1.2.3"` 等解析失败 → 该组分**不计入合计**，
  但合计仍按"完整"对外呈现。
- **后果**：若人工对该条选"通过"，则该行带着**不完整的合计**落账，
  "无容差 >100 一律报"被绕过。
- **建议**：解析失败时给出**行级**标记"本行合计不可信"，而不只是单格 warn。

#### M6. 重跑会清空用户直接填在 Excel 里的决定

- **位置**：`write_review` 整表重写，脚本从不读回 `task_review.xlsx`
- **现象**：用户直接在「问题清单」的"员工决定"列填写、但**没整理成 `decisions.json`**，
  下次重跑该列被清空。
- **后果**：人工输入被静默覆盖。手册第 6 节要求人把 Excel 整理成 `decisions.json`，

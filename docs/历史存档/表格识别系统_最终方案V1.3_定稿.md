## 0. V1.2 → V1.3 改了什么（共 9 项）

1. **工作方式改为"任务级集中审核"**：识别中发现问题不再当场打断操作人员，全部先记入"问题账本"；当天所有图片跑完后，一次性集中人工判断。
2. **数据分五层，未确认的绝不进事实表**：证据层（raw.json）/ 工作层 / 问题账本 / 规则层 / 事实层（final.xlsx、台账）。
3. **状态改两层**：行级"机器状态"+ 任务级"流程状态"；REVIEW 不再代表"马上问人"。
4. **归档改为最后一个动作**：先出"归档计划"→ 人工确认 → 统一执行 → 移动后复核并留 manifest。
5. **机器不再补造任何数据**：含取消"杂分（计算）"——杂栏目有值照录、空白留白，不做任何计算补值；事实表的"derived（计算生成）"概念随之取消。**这是用户本轮拍板，全系统生效。**
6. **事实表字段瘦身与分工**：过程字段（row_role、category、count_in_total、name_status）留在工作/规则层；事实表保留"原始值原文"和"成分原名"（用户拍板保留，查错溯源全靠它）。
7. **人工审核界面固定为 4 个 Sheet**：审核总览 / 问题清单 / 待审核数据 / 文件归档清单；员工只需处理"问题清单"，其余默认接受。
8. **写入 15 条"落地硬规则"**（第 11 节）：全部来自本机实机排查，不是理论——包括一个会导致"正确数据被误报为错误"的浮点陷阱（本机实测 2.4 万组正确数据里误报 94 次）。
9. **新增边界处理**：增行/删行/改结构走对话（不在 Excel 硬做）；员工排序筛选不影响决定归属；重跑不冲掉已填决定（详见 8、9 节）。

## 1. 背景、环境与目标

### 1.1 实际环境（已确认）
- 运行载体：Codex（桌面），会话已接入视觉模型（本文称 DSV4），可直接看图片并读写本地文件。
- 本机已装：Python 3.12.10、openpyxl 3.1.5、pandas 3.0.3、Pillow 12.1.0（无需新装依赖）。
- 不引入：第二套视觉 API、本地 OCR 引擎、SQLite/向量库、DSPy/TextGrad、GUI/Web/Docker、模型路由。
- 数据无需保密，可直接用公共云视觉能力。
- 载体策略：**当前用 Office Excel 承载，数据结构按数据库思想设计（为将来迁移预留）**；首版不引入数据库。产物保持 WPS 兼容底线（不用宏/VBA、不用新版专属函数）。

### 1.2 业务对象（来自真实单据）
- 全公司业务单据类型大概率不超过 10 类，新增频率不高，偶尔调整。
- **重要前提**：公司正在重新设计全部业务单据，以适配一线员工填写并便于数字化。因此**表头、单位、命名格式一律不提前冻结**；改版即视为同一业务表的新版本，重新注册后生效，旧版 schema 永久保留以读取历史照片。
- 库存日报：一张图含两个逻辑表（库存明细 / 现场库区明细），底部有合计行。
- 来料化验分析：每批来料若干桶，一行=一桶/一个样品；同一批料可能由多张照片组成。
- 成分明细形态：成分名与百分比各自独立成格（例：甲醇 | 30% | 乙醇 | 40% | IPAC | 10% | 高沸物 | 5% | 杂 | 15% | 含水量 | 5%），可逐格取数。
- 数值均为明示值，无需正负号约定或不等号语义；计算交给 Excel 函数/Python。
- 单据没有"判定/合格/结论"类字段，不设该列。

### 1.3 目标优先级
结构正确 > 业务语义正确 > 可计算 > 视觉原样还原。
- 普通图片一次识别直接产出 Excel；不确定的事集中问一次；宁可多问一次也不猜。
- 数据详实可查、可追溯；支持 Excel 函数/透视表/Python 分类计算与会议图表。
- 越用越准，且进化不破坏已有能力。

## 2. 总体架构

**云视觉大模型（负责"看"）+ Codex（负责"编排与判断"）+ 本地 Python（负责"裁判与落盘"）+ 规则文件（负责"记住怎么算"）+ 人（负责"最后拍板"）。**

一句话流程：图片进来 → 看 → 校验 → 有疑问先记账 → 当天全部跑完 → 人集中拍板一次 → 程序全量重跑 → 生成最终 Excel 与归档 → 关闭任务。

## 4. 数据模型：五层分工（不许揉在一起）

### 4.1 证据层（只读，写完不改）
- `raw.json`：模型"看见什么"的原文（含 uncertain 列表）。
- 原图副本 + 文件指纹（SHA-256）+ 原名↔业务名映射。
- 规则：证据层永不修改；改数据一律通过"给出新决定 + 重跑"的方式产生新结果。

### 4.2 工作层（可重算，绝不进台账）
- 每行数据带"机器状态"：`ok`（无问题）/ `pending`（有待人工判断的问题）/ `blocked`（硬错误，如合计超 100%）。
- 工作层字段最全（含所有过程字段：row_role、category、count_in_total、name_status、候选值、问题引用）。
- 规则：工作层可反复重算；**它永远不会直接变成事实表**——只有"人工确认后的重跑结果"才进事实表。

### 4.3 问题账本（issues.json）
每条问题固定字段：
`issue_id / run_id / type / severity / image / sheet / target_ids（影响范围）/ description / candidates（候选值）/ machine_status / human_decision`
- `target_ids` 是"影响范围"：一条决定自动作用到所有受影响行，避免"只改了一条、其他同类还是错的"。
- 首版问题类型 7 种：`OCR_UNCERTAIN`（看不清）、`CONFLICT`（同对象同字段两个值）、`DUPLICATE`（完全重复来源，信息级）、`COMPONENT_SUM_OVER_100`（组分合计超百）、`UNREGISTERED_TERM`（没见过的成分词）、`MISSING_REQUIRED_FIELD`（关键字段空）、`DATE_AMBIGUITY`（日期歧义/冲突）。
- 其余类型（行数异常、归档冲突等）先不做，等真出现再加。

### 4.4 规则层（改了要人同意 + commit）
- `schemas/*.json`：某模板的 Sheet 名、列定义、列顺序、别名、category/count_in_total。
- `aliases.json`：成分名归一（含水量/水分/水 这类词的注册结果）。
- 规则层的变化必须留下记录，可回滚。

### 4.5 事实层（只含已确认）
- `final.xlsx`：每任务一份，只含已确认的数据行；可重复生成（同一任务重跑覆盖自身，不影响历史）。
- 长期台账（阶段 2 再开）：只追加；只从 golden（人工确认过的历史）重建。

**事实表（成分长表）字段（定稿）：**

| 字段 | 说明 |
|------|------|
| record_date | 业务日期（真日期类型） |
| source_type | inventory / incoming |
| location | 储存位置/区域 |
| batch_id | 批次号（文本） |
| container_id | 桶号/容器号（文本） |
| material_name | 物料名称 |
| supplier | 厂商/来源（有则填） |
| component_standard_name | 成分标准名（已确认后填写） |
| component_original_name | 成分原名（**保留**，审计证据） |
| numeric_value | 数值（Python 转换后） |
| unit | 单位（% / pH / 吨…） |
| raw_value | 图上原文（**保留**，用户拍板） |
| source_run_id | 来源任务编号（可回溯到原图） |
| source_row_id | 来源行号 |

已移出事实表（留在工作/规则层）：row_role、name_status、category、count_in_total、候选值、问题引用。
说明：因"机器不再造数"，事实表**没有** derived 行——每一行都来自图上原文或人工决定。

## 5. 组分合计校验（最终定稿规则）

对每个"来源对象"（某图某物料/某桶的成分集合）：

1. 求 **C = 所有应计入合计的组分之和**，其中：
   - 不计入的水分类指标（含水量/水分/水/水份，注册后确认）不计入；
   - "杂"类词单独处理（见下），不并入 C。
2. 判定（**无容差**）：
   - **图上有"杂"且该格有数值 m**：若 `C + m > 100%` → 问题（严重），该对象 blocked，进问题清单；否则通过。
   - **图上有"杂"但空白**：若 `C > 100%` → 问题（严重）；否则通过，**杂留白**。
   - **图上无"杂"**：若 `C > 100%` → 问题（严重）；否则通过。C 不足 100% 不补、不提示（总览区只做信息展示）。
3. **任何情况下，机器都不补造数值**（不生成"杂分（计算）"，不改写空白）。
4. **实现硬要求（实机验证）**：求和一律**换算成整数计算**（例如以 0.01% 为单位：`C_int = Σ round(v×100)`，与 10000 比较），或使用 Decimal。**禁止用浮点数直接相加**。
   原因（本机实测）：在 23,804 组"数学上精确等于 100%"的真实数据中，用浮点直接相加有 **94 组**算成 `100.00000000000001`（如 11.3+0.2+8.3+12.3+67.9），会被"超 100% 一律报错"规则**误判**；改用整数计算后误报为 **0**。
5. 超 100% 的处理路径：该对象不落账 → 记入问题清单（附候选值）→ 人工对照原图给出正确值 → 重跑校验 → 通过后落账。不设"近似放行"。

## 6. 任务流程与状态机

```
收图 INPUT（inbox / 聊天贴图 / 本地路径）
  ↓
分类 CLASSIFY（已知表型 / 新表型）
  ├─ 已知表型 → 逐图识别 EXTRACT（问题随手记，不打断）
  └─ 新表型 → 一次性结构提案 ASK_SCHEMA → 人确认 → 注册 REGISTER → 继续识别
  ↓
问题记账 ISSUE_RECORDING（写 issues.json；数据留在工作层）
  ↓
全部跑完 READY_FOR_REVIEW（生成 task_review.xlsx）
  ↓
人工集中审核 HUMAN_DECISION（只处理问题清单；写 decisions.json）
  ↓
收尾全量重跑 FINALIZE + REVALIDATE（从 raw.json + decisions.json 重新生成一切）
  ↓
生成最终 Excel（facts 层）
  ↓
执行归档 ARCHIVE（最后动作；逐条 manifest）
  ↓
归档复核 → CLOSED（生成任务报告）
```

**"一张图出问题会不会停整个任务"**：不停。只有两种情况例外：
1. 新表型的结构还没人确认 → 该类图片暂挂（连"哪列是什么"都不知道，硬跑必错），其余照常；
2. 全部图片处理完、还没到人工审核环节 → 任务停在"待审核"，等你有空处理。

## 7. 问题账本：三类事情的区分（本设计的核心）

| 类别 | 定义 | 数据去向 | 能不能进事实表 |
|------|------|----------|----------------|
| 已确认事实 | 图上清楚 + 校验全绿 | 工作层 ok 行 | 会（重跑后） |
| 待人工判断 | 看不清/冲突/没见过的词 | 工作层 pending 行 + 问题账本 | **复核通过前不能** |
| 未解决 | 人没处理的 pending / blocked | 留在工作层与问题账本 | **不能**（留到下次，不偷偷进） |

一句话原则：**问题可以延后，人不能被绕过；机器绝不替人猜。**

## 8. 人工审核包（task_review.xlsx）

四个 Sheet：

1. **审核总览**：今天几张图、几个业务表、多少行、多少问题、多少冲突、多少看不清、多少合计超百、多少新表型、归档几个文件、还剩几个未解决。
2. **问题清单**（唯一需要填写的地方）：一行一个问题：
   `问题编号 | 图片 | 表 | 对象（批次/桶/字段） | 问题描述 | 候选A | 候选B | 员工决定（下拉或手填） | 备注`
3. **待审核数据**：今天准备落账的数据（只读展示，用于"今天 AI 到底录了什么"）。
4. **文件归档清单**：原名 → AI 建议名 → 目标目录 → 员工确认列。

使用规则（写进操作手册）：
- **只填"问题清单"**。没有问题的数据不用逐个确认（否则 200 行会看死人）。
- 填写约定：**按纸上原样填**（纸上有 % 就带 %，带单位就带单位）；系统会自动按列类型解析，并在任务报告里回显"你填了什么 → 系统记成什么"，对不上会再问。
- 审核结束前系统检查"是否还有未解决"，有则提示；坚持结束 → 未处理的对象不落账（其余正常）。
- **增行/删行/改表结构**：不在 Excel 里硬做，直接在对话里说（如"第 3 行后面漏了一桶，数据是…"），由 AI 改 raw.json 后重跑。
- 填完保存关闭 Excel，再说一句"审核完成"；程序读取决定 → 全量重跑 → 生成 final.xlsx。
- 员工随时可用"数行数 → 扫日期/位置/名称 → 处理问题清单"三步核对。

## 9. 收尾、重跑与归档

### 9.1 收尾全量重跑
- 人工决定后，从 `raw.json + decisions.json` **重新生成全部结果**（不用增量修补）。
- 重跑前先把已填决定回填（重跑生成的审核包必须带上已有决定，绝不冲掉员工填过的内容）。
- 这是"改完了但旧结果还残留"类问题的根治办法（业界称 Complete Rebuild，是成熟做法）。

### 9.2 归档三原则
1. **最后动作**：识别阶段只生成"归档计划"；人确认后才真正移动。
2. **永不覆盖**：移动只用 `os.rename`（Windows 遇同名直接报错 → 自动加 `_2`、`_3` 后缀）；禁止 `os.replace`（静默覆盖）与 `shutil.move`（官方文档明确"may be overwritten"）。
3. **逐条 manifest**：移动一条记一条（源、目标、成功/失败、时间）；中断可续，失败清单下次只补未成功的。

### 9.3 归档前洗名字
- 先替换 Windows 非法字符 `\ / : * ? " < > |` 为 `-`（实测：含 `:` 的名字会生成 0 字节假文件 + 隐藏数据流，看起来像空图）。
- 业务名长度 ≤ 80 字（实测 250 个汉字仍可行、260 个失败；80 字留足安全余量）。
- 归档路径保持浅（日期目录 + 必要时一层批次目录），不做深层层级。

## 10. Excel 工程规则（openpyxl）

- 类型由 schema 决定，不让 Excel 猜：identifier/文本列写前设 `@`；percent 存分数 + `0.0%` 格式；数值存数值 + 格式；日期存真日期。
- 不创建合并单元格。
- **审核包内不写任何公式**（程序读不到公式结果；也避免"重算失败"类问题）。首版全程不自动生成公式。
- 数据验证下拉：候选列表超 255 字符时改手填（Excel 硬限制）。
- 决定单元格一律文本格式（防 Excel 自动把 `1-4` 转成日期、把 `0.85%` 转成百分数小数）。
- 决定按"问题编号 + 行 ID"关联，不按行号——员工排序、筛选、甚至删掉空行都不影响。

## 11. 落地硬规则（本机实机排查结论，共 15 条）

| # | 发现（实测证据） | 硬规则 |
|---|------------------|--------|
| 1 | 23,804 组"精确=100%"数据中，浮点相加 **94 组算成 100.00000000000001**，会被"超100%报错"误判 | 合计一律整数运算（0.01% 为单位）或 Decimal；禁止浮点直加 |
| 2 | `os.rename` 遇同名目标 → FileExistsError（拒绝）；`os.replace` → 静默覆盖成功 | 归档只用 `os.rename`；禁用 `os.replace` 做归档 |
| 3 | Python 官方文档：`shutil.move` 目标同名时 "may be overwritten" | 归档禁用 `shutil.move` |
| 4 | 文件名含 `:`（如时间 9:30）→ 生成 0 字节假文件 + 隐藏数据流 | 自动命名先洗非法字符；含冒号名字一律替换 |
| 5 | 文件被占用时写入 → PermissionError 5（用独占句柄复现；本机无 Office，未能复现真实 Excel 锁，按同机制处理） | 收尾不覆盖员工可能打开的文件；写失败则提示"请关闭 Excel 后重试" |
| 6 | 文件名 250 个汉字可建、260 个失败（NTFS 上限） | 业务名 ≤ 80 字；超长自动截断 |
| 7 | 12 MB 文件 SHA-256 仅 13.3 ms | 用内容指纹做"重复提交"检测，代价可忽略 |

## 12. 自进化与规则管理

- 反馈分级：偶发错误只记 FEEDBACK_LOG；规则性问题（同类错误反复出现或用户明确要求）→ 进化提案 → 用户同意 → 改允许文件 → 小样本回放历史 golden 回归 → 通过 → git commit；失败 → git restore。
- FEEDBACK_LOG 条目：FB-ID、affected schema、字段、模型输出、人工正确答案、occurrence、错误类型、处理方式、状态。
- 新规则必须注明 replaces/related_to；冲突或重复时人工清理。
- 不可修改（AI 永不自动动）：validate_export.py、既有 golden 条目、既有 schema 核心列定义。
- 可修改：新增 schema（经提案确认）、规则文本、FEEDBACK_LOG、aliases（经用户确认）。
- 成分归一红线：原名永远保留；标准名只在确认后填；新词一律走"提案→拍板→写词典"。

## 13. 失败恢复方案

| 情况 | 处理 |
|------|------|
| 程序中途崩溃 | 每图处理完即落盘（一图一个 raw 片段）；重跑按文件指纹跳过已完成 |
| Excel 生成失败 | 证据层/工作层数据都在，可随时重生成；失败原因记入任务报告 |
| 人工审核中断 | decisions.json 逐条保存，下次继续，不必重填 |
| 归档失败 | 逐条 manifest + 失败清单；重跑只补未成功项 |
| 重复提交同一张图 | 内容指纹识别 → 提示"这张已处理过"，不产生第二份数据 |
| 重复运行同一天任务 | 任务号唯一；重跑覆盖当天工作层，不追加 |
| 员工重拍替换了某张图 | 以最后提交的为准；旧图归档标记 superseded，数据以新图结果落账 |
| schema 注册失败 | git 可回滚；注册前自动 commit 当前状态 |

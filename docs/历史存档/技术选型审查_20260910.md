## 一、结论先行

**架构选型是对的，没有明显"造轮子"。**

本系统的核心是「**云视觉模型看图 → 出 raw.json → 确定性脚本当唯一裁判 → 人一次性审核**」。
其中"看图"这一步走的是 **OCR-free 文档理解**路线（直接把图变成结构化字段，不做 OCR 文字流水线），
这正是当前学术与工业界的主流方向（Donut/LayoutLM 一路演进到今天的 VLM），
**不是落后方案，而是前沿方案**。

真正值得动手的只有 **2 处**，其余"更先进"的替代品对本场景是**负收益**，见第五节。

| 类别 | 现状 | 判断 |
|------|------|------|
| 看图（识别） | 云视觉大模型，无本地 OCR | ✅ 保留。可选加"离线 OCR 交叉验证" |

**关键判断（重要，别被 star 数带偏）**：

1. **你的输入是"手机拍的纸质表单"，不是 PDF。**
   MinerU / Docling / Marker / PDF-Extract-Kit **都是 PDF 优先**，
   它们解决的是"复杂的电子 PDF 怎么拆成 Markdown"——**和你的问题不是同一个问题**。
   直接拿过来是错配，不是升级。

2. **能力对得上的是 PaddleOCR 和 Surya**（图片优先）。
   PaddleOCR 的 README 明确声明：PP-OCRv6「+4.6% 检测 / +5.1% 识别」、
   「**超越主流 VLM**（Qwen3-VL-235B、GPT-5.5），仅 34.5M 参数」、
   「CPU 端到端提速 5.2×」、支持 **ONNX Runtime / CPU 离线**、
   并且其 PaddleOCR-VL「**适合手写文本**与历史文档」。
   —— 注意：**这是厂商自述指标，且比的是"文字识别准确率"，
   不等于"一张单据 → 结构化字段"的端到端准确率**。这两个指标差得很远。

3. **所以不建议用开源 OCR 替换云 VLM。** 在"手写 + 拍照 + 倾斜 + 光照差"的组合下，
   专用 OCR 的**字段级**准确率通常仍低于前沿 VLM；替换会让问题清单变长，
   直接推高人工审核成本——那才是你真正的成本大头。

4. **真正值得做的是"第二证据源"**：用 PaddleOCR 离线跑一遍，
   把识别出的文字当作**交叉验证证据**，只有两边都认下来的才自动放行，
   不一致的进问题清单。这**正好服务你的"不猜 / 不造数"红线**——把"单点信任模型"
   变成"双源互证"。

**代价（必须说清）**：引入 PaddleOCR = 引入 paddlepaddle（数百 MB）+ 模型权重，
安装复杂度和离线包体积大幅上升，与你现在"换电脑双击一下就好"的极简部署**相冲突**。

> **建议（已更正）：不引入本地 OCR。**
>
> 初版建议"先不要动，等积累照片后做 A/B 实验"——**该建议撤回**，理由：
> 1. **撞红线**：`架构说明.md` 第八节明确写着"**不装本地 OCR**"，且理由正当
>    （"每一条都会增加出错的可能性和维护负担"）；
> 2. **路线倒退**：本项目现在是"图 → VLM → 结构化 JSON"，属于 **OCR-free 文档理解**，
>    这是当前主流前沿路线；在 VLM 之外再叠传统 OCR 流水线，是把已经绕过的东西请回来；
> 3. **误差是累积而非互补**：传统流水线"检测错→识别错→结构错→填充错"逐级放大，
>    在拍照/手写/倾斜场景下比 VLM 崩得快，结果是大量**假警报**涌入问题清单，
>    反而推高最贵的人工审核成本；
> 4. **对齐成本被低估**：要让 OCR 的字符框与 VLM 的字段对应，需做空间坐标对齐，
>    这本身是一块不小的工程，且它自己也会错。
>
> **唯一例外**：若将来出现**具体、可复现**的误读痛点（例如某类单据的手写数字稳定读错），
> 再**针对性**评估单点方案，而不是整体引入 OCR 流水线。
>
> **替代方向**：见本节末尾"防编造的更轻办法"。

#### 防编造的更轻办法（零新增依赖，本次审查的实际发现）

"怕模型编数"是对的，但解法不是加第二个识别引擎，而是**用足模型自己给出的两份表述**。

本项目 `raw.json` 的结构里，每个成分**本来就同时有 `raw_value`（图上原文）和 `value`（转换后小数）**——
这是很好的设计。但实测 `validate_export.py` 发现一处**未闭合的不一致**：

| 位置 | 代码 | 优先取用 |
|------|------|----------|
| 合计校验（`validate_export.py:311`） | `raw = comp.get("raw_value", comp.get("value"))` | **`raw_value`** |
| 最终 Excel 落账（`validate_export.py:518`） | `"numeric_value": comp.get("value", comp.get("raw_value", ""))` | **`value`** |

**问题**：合计是按 `raw_value` 算的，写进 Excel 的却是 `value`。
**当两者不一致时，现有校验不会发现**——等于"校验基于一个数、交付另一个数"。

例：`raw_value: "89.6%"` 配 `value: "0.896"` 正常；
但若模型写成 `value: "8.96"`，合计照样通过，Excel 里落的是错值。

**建议**：增加一条"**`raw_value` ↔ `value` 一致性校验**"——
把 `raw_value` 按同一套 `parse_percent` 换算后与 `value` 比对，不一致即进问题清单。

- ✅ 零新增依赖（不需要任何 OCR）
- ✅ 用足已有的双字段设计，属于"模型自己的两份表述互相印证"
- ✅ 完全契合"不猜 / 不造数"红线
- ⚠️ 需修改 `validate_export.py`，而该脚本**只能由人修改** → 须用户拍板

### B. 校验（"唯一裁判"）—— 造轮子嫌疑最大，但拆开看站得住

**现状**：`validate_export.py` 870 行自研，含结构校验、类型转换、合计校验、问题账本、Excel 生成、归档。

**拆成两半看**：

| 部分 | 内容 | 能否用库替代 |
|------|------|--------------|
| **通用部分** | raw.json 的结构/类型/必填/枚举校验 | ✅ 能，而且应该用库 |
| **业务部分** | 合计>100% 无容差、水/杂归类、问题账本、归档计划、撞名加序号 | ❌ **没有任何库提供**，必须自研 |

候选库实测：

| 库 | Stars | 最新版(发版) | 适配度 |
|----|-------|--------------|--------|
| **pydantic** | 28,762 | 2.13.5 (2026-08) | 高（但见下方⚠️） |
| **jsonschema** | — | 4.26.0 (2026-01) | 高（纯 Python，零编译） |
| **pandera** | 4,452 | 0.33.1 (2026-09) | 中（面向 DataFrame 统计校验） |
| **great-expectations** | — | 1.23.0 (2026-09) | **低（过重）** |
| frictionless | — | 5.19.0 (2026-04) | 低 |
| cerberus | — | 1.3.8 (2025-11) | 低 |

⚠️ **一个反直觉但对你很重要的点**：
Pydantic v2 的核心是 Rust 写的（`pydantic-core`），**发布的是按平台+Python 版本区分的编译 wheel**。
你的整个部署哲学是"**离线 wheel + 换电脑双击就好**"——
引入 Pydantic 意味着你得为**每台新电脑的 Python 版本**准备对应的编译包，很容易翻车。
**`jsonschema` 是纯 Python，vendor 一个 wheel 到哪都能装**，与你的离线策略天然契合。

**但要提醒红线**：`validate_export.py` **只能由人修改**。引入任何库都等于改裁判脚本，
**必须你本人拍板**，我不能自动改。

### C. Excel 读写 —— 保持不变，别折腾

| 库 | 最新版(发版) | 能力 |
|----|--------------|------|
| **openpyxl（现状）** | 3.1.5 (2024-06) | 读 + 写，事实标准 |
| XlsxWriter | 3.2.9 (2025-09) | **只能写**，不能读回 |
| fastexcel | 0.21.0 (2026-08) | **只能读**，Rust 极快 |
| python-calamine | 0.8.2 (2026-07) | 只能读，Rust |
| pylightxl | 1.61 (2023-01) | 轻量，功能弱，已停滞 |

**结论：继续用 openpyxl。** 理由：
1. 你的脚本既要**写** `final.xlsx`/`task_review.xlsx`，又要能**读回**校验 → 只有 openpyxl 两样都行；
2. 换 XlsxWriter 收益极小（写入速度快一点），但要重写全部 Excel 代码，且失去读回能力；
3. openpyxl 两年没发新版 ≠ 有问题，而是**功能已经稳定**。它仍是 xlsx 生态的事实标准。

**将来唯一值得加的是"读"**：数据量大后要读大 Excel 做回归测试时，
用 `fastexcel` 或 `python-calamine`（Rust，速度快一个数量级），**写入仍用 openpyxl**。

### E. 技能格式 —— 这里确实"有轮子"，而且我找到了

**重要发现**：存在一个**跨工具的开放标准 —— Agent Skills（agentskills.io）**。
Anthropic 官方 Claude Code 文档原话：

> "Claude Code skills follow the **Agent Skills open standard, which works across multiple AI tools**.
> Claude Code extends the standard with additional features like invocation control,
> subagent execution, and dynamic context injection."

即：**基础格式是标准，Claude Code 只是超集**。Anthropic 仓库里有 `spec/`（规范）和 `template/`（模板）。

**你的合规情况**：

| 项 | 官方 template | 你的 SKILL.md | 结论 |
|----|---------------|---------------|------|
| frontmatter 字段 | `name` + `description` | `name` + `description` | ✅ 一致 |
| name 取值 | `template-skill`（小写+连字符） | `image-data-recognition` | ✅ 符合命名惯例 |
| 附加字段 | — | `metadata.short-description` | 🟡 属扩展字段，需确认标准是否允许 |

**建议**：核对 `agentskills.io/specification` 全文（我这边被网络挡住取不到），
重点确认三件事：① name 的字符与长度限制；② description 长度上限（过长会被截断）；③ 自定义 `metadata` 是否合规。
你的 `description` 写得比较长，且**把"工作区在哪"这种运行时信息写进了触发描述**——
按标准，`description` 是给模型判断"该不该用这个技能"的，塞运行时逻辑可能两头不讨好。

**你自研的 `安装技能.py`（自动探测 7 个工具的目录 + 写 workspace.txt）**：
标准**不覆盖**"往各工具安装"这件事，所以这部分属于**合理自研**，不算重复造轮子。
除非官方将来给出统一的安装 CLI。

5. 单日单据 >50 张 → 上 **DuckDB** 做回归测试与统计。

## 六、一句话总结

**这套系统没有明显的重复造轮子：**
"看图"用了当前最前沿的路线（VLM 直接出结构化数据，不做 OCR 流水线），
"裁判"里的业务规则是任何库都给不了的领域逻辑，
Excel 用的 openpyxl 就是当前最新版。

**唯一被遗漏的"现成的轮子"是 Agent Skills 开放标准**（技能格式规范），建议核对合规。

**技术侧真正值得补的不是引入 OCR，而是补上 `raw_value` ↔ `value` 一致性校验**——
零新增依赖，直接堵住"校验用一个数、交付另一个数"的静默漏洞。

**关于 OCR 的结论（更正后）**：本项目"直接看图出结构化数据"的路线**本身就是最先进的**，
**不需要也不应该**引入传统 OCR 流水线；那条建议已撤回。

## 一、本机实机验证（当天真跑，不是理论）

| # | 测试项 | 实测结果 | 对方案的影响 |
|---|--------|----------|--------------|
| 1 | Windows 上把 a.txt 改名为已存在的 b.txt | `os.rename` → **FileExistsError（拒绝覆盖）**；`os.replace` → **静默覆盖成功** | 归档必须用 `os.rename`（会拒绝覆盖），**绝不能用 `os.replace`**（会悄悄吃掉同名文件） |
| 2 | 目标文件正被占用时替换 | `os.replace` → **PermissionError 5（拒绝访问）** | 收尾写文件前必须检测占用；失败要自动换新文件名并告知，不能假装成功 |
| 3 | Python 官方对 `shutil.move` 的定义 | 原文："If dst already exists but is not a directory, **it may be overwritten**" | 归档**不能**用 shutil.move 盲移；必须先查重名再移动 |
| 4 | 文件名里带冒号：`批次9:30化验.jpg` | 实际生成的是 **0 字节的"批次9"** + 一个隐藏数据流；文件夹里看着像空文件 | 自动命名必须**先洗掉 Windows 非法字符**（`\ / : * ? " < > \|`），否则文件"看起来存在、实际是空的" |
| 5 | 325 字符超长中文路径 | 本机 Python 可以创建和读取；但资源管理器不保证 | 归档路径保持短（天数目录 + 批次目录两层即可），不要层层嵌套 |
| 6 | 12 MB 文件算 SHA-256 | **13.3 毫秒** | 用"文件内容指纹"做重复检测，代价几乎为零 → 重复上传可以被机器直接识别 |
| 7 | openpyxl 审核表往返 | 批注、下拉选项、条件格式、人工改格后读回，**全部正常**（本地读取显示写入前 None → 人工改 0.85 → 读回 0.85） | "员工在 Excel 里改，程序读回决定"这条路走得通，无需自建界面 |
| 8 | Excel 文件被打开时程序写它 | 本机无真实 Excel 无法完全复现，但按 Windows 锁定机制与第 2 条：**会失败** | 收尾一律"写新文件"，不要覆盖员工正打开的那个审核文件 |

**结论：V1.3 提出的"归档计划 → 人工确认 → 最后统一执行 → 移动后再校验"是必要设计，不是过度设计。**

## 三、逐条回答审稿问题（按要求的 A–M）

### A. 最终结论

**基本通过但必须修改。** 不通过的原因不存在；但若按 V1.3 原文原样实现，会在"归档覆盖""未确认数据污染事实表""人工改完旧结果残留"三处出事——这三处修好即可开工。

### B. 必须修改（只列会造成数据错误/不可恢复的）

1. **归档顺序改成"最后动作"**：识别阶段只产出 `archive_plan.json`（改名建议 + 目标目录 + 新名），人工审核确认后才真正移动。
   - 移动必须用 `os.rename`（Windows 遇同名直接报错 = 天然防覆盖），不得用 `os.replace`、不得用 `shutil.move` 盲移。
   - 每次移动**逐条写 manifest**（成功一条记一条），中途崩溃也能知道移到哪了。
   - 重名自动改名（追加 `_2`、`_3`），**永不覆盖**；文件名先洗非法字符。
2. **数据三层分离，未确认的绝不进事实表**：`raw.json`（证据层，只读不改）→ `working/pending`（待确认工作区）→ `facts`（已确认事实，只追加）。台账/事实表只能由第三层生成。
3. **状态改两层**：行/对象级 `machine_status`（自动校验结果）+ 任务级流程状态（收图/识别/待审核/收尾/已关闭）。删除"REVIEW = 马上问人"的含义，REVIEW 只表示"进问题账本"。
4. **问题账本带"影响范围"**：每个问题记 `applies_to`（受影响的全部行/对象 ID）。一个人工决定一次性作用到所有受影响记录，避免"只改了一条、其他同类还是错的"。
5. **收尾全量重跑**：人工决定后，从 `raw.json + human_decisions.json` 重新生成全部结果，不做增量修补。这是"旧结果残留"的根治办法（对应 Fowler 的 Complete Rebuild）。
6. **人工决定必须落盘**：`human_decisions.json` 是唯一权威记录，Excel 只是填写界面。防止"文件被改名/覆盖后决定丢失"。

### C. 建议修改（提高可靠性，可后置到第二阶段）

- 17 种问题类型首版只做 6 种：`OCR_UNCERTAIN`（看不清）、`CONFLICT`（同对象同字段两个值）、`DUPLICATE`（完全重复来源）、`COMPONENT_SUM_OVER_100`（合计超百）、`UNREGISTERED_TERM`（没见过的成分词）、`MISSING_REQUIRED_FIELD`（关键字段空）。其余等真出现再加。
- 事实表瘦身：把"过程字段"移出事实表（`row_role`、`name_status`、`category`、`count_in_total`）；保留 `component_original_name`（原名，便宜且是审计证据）、`source_run_id`/`source_row_id`（最小追溯）。`raw_value` 是否保留由用户拍板（见第四节）。
- 重复检测分两层：先做"文件级完全重复"（内容指纹，13 毫秒能算完），再做"业务级重复/冲突"（同对象同字段同值 = 重复；不同值 = 冲突）。
- EXIF 拍摄时间可作为"图内日期"的交叉校验（Pillow 已装），但只做校验不做主依据（微信/QQ 传图会抹掉 EXIF）。

### D. 可以不做（现在看起来高级、首版没必要）

- 单独的"observation 数据库"——`raw.json` 本身就是观察层，不需要再建一层。
- 复杂增量重算——全量重跑足够快（你的数据量是每天几张图）。
- 自动把某决定推广到"相似问题"——精确 `applies_to` 列表就够了。
- 版式指纹/相似度评分平台——用"是否会把数据放错列"这个简单判据替代（见第 13 条回答）。
- 维持 V1.2 全部红线不变（第二视觉 API、向量库、数据库、DSPy 等）。

### G. 最终数据模型边界（四样东西不许揉在一起）

```
证据层   raw.json / 原图 / 文件指纹        —— 只读、不改、不删
工作层   带状态的行数据（pending/ok）      —— 可改、可重算，绝不进台账
```

四层的连接键：`source_run_id` + `source_row_id`（从事实能一路查回原图）。

```
                                                                        ↓

                                                                        ↓
                                                        人工集中审核 HUMAN_DECISION
                                                                        ↓

                                                                        ↓
```

### J. 最终员工审核界面（4 个 sheet + 3 条规则）

1. `审核总览`：今天几张图、几张表、多少行、多少问题、多少冲突、多少新表型、归档几个文件、还有几个没解决。
2. `待审核数据`：今天准备落账的数据（只显示有问题的行 + 可展开全部）。
3. `问题清单`：一行一个问题，含候选值和员工决定列（下拉选择，已有实测支持）。
4. `文件归档清单`：原名 → 建议名 → 目标目录 → 确认列。

三条规则：
- **没有问题的行不需要员工逐个点确认**（否则 200 行会看死人）。员工只需处理"问题清单"，其余默认接受。
- 审核结束前，系统检查"是否还有未解决问题"，有则提示；员工坚持结束 → 未解决的行**不落账**（留到下次），其余照常落账。
- 审核完成后**不是直接改 Excel**，而是全量重跑（B5）。

### K. 失败恢复方案

| 情况 | 处理 |
|------|------|
| 程序中途崩溃 | 每张图处理完即落盘（raw.json 一图一个）；重跑时按文件指纹跳过已完成的 |
| Excel 生成失败 | 保留 raw/工作层数据，可随时重生成；失败原因记入 issues |
| 人工审核中断 | decisions.json 逐条保存，中断后继续，不必重填 |
| 归档失败 | 逐条 manifest + 失败清单，下次重跑只处理未成功的（幂等，对应 Stripe 模式） |
| 重复提交同一张图 | 内容指纹（SHA-256）识别 → 提示"这张已处理过"→ 不产生第二份数据 |
| 重复运行同一天任务 | 任务号唯一；重跑 = 覆盖当天工作层，不追加 |
| schema 注册失败 | git 可回滚；注册前自动 commit 一次"注册前状态" |

### L. 关键测试案例（我按你的业务挑了 12 个，比 20 个更聚焦）

1. 20 张已知表型正常处理，其中 2 张有数字看不清 → 是否只产生 2 个问题、其余正常落账。
2. 3 张属于同一新表型 → 是否只问一次结构、3 张一起处理。
3. 同批次同桶号两张图数值 0.35 / 0.38 → 是否成为"冲突"等待人工，而不是自动选一个。
4. IPAC 99.5% + DMF 0.8% → 除水外合计 100.3% → 是否报问题。
5. IPAC 99.5% + DMF 0.3% + 杂=空白 → 合计 99.8% → 是否正常通过（不造数）。
6. 同一张照片上传两次 → 是否识别为重复、不产生第二份数据。
7. 自动命名与已有文件同名 → 是否自动加后缀而不是覆盖。
8. 员工同时改了文件名和一条数据 → 两者是否都被正确执行。
9. 员工解决冲突后重跑，又发现另一行合计超百 → 是否二次报问题而不是放过。
10. 员工没解决某问题就结束 → 该行是否没进事实表，其余是否正常。
11. 员工忘记关 Excel 就点收尾 → 是否安全失败并提示关闭。
12. 文件名里含 `:` 或 `/`（比如写时间 9:30）→ 是否被清洗成安全名字。

## 四、需要用户拍板的 3 件事（不由 AI 决定）

1. **"杂"写了但数值格是空的，怎么办？**（两份文件不一致，必须你定）
   - 选项 A（你上一轮的决定）：系统补算 100%−其余，标"计算值"。
   - 选项 B（GPT 本轮提案）：什么都不补，留白。
   - **选项 C（我推荐）**：系统**不自动补**，但把它列成一条问题、附上候选值（100%−其余），审核时你点一下确认 → 数据来自你的确认，不是机器造的。既不需要机器造数，也不会白白丢掉一个格子。
2. **事实表要不要保留"原始值原文"这一列？**（比如图上写的是"0\.6%"的原文）
   - 推荐：保留（成本几乎为零，将来查错全靠它）。其余过程字段移出。
3. **员工审核时，是否需要逐张图看一遍，还是只看"总览 + 问题清单"就够？**
   - 推荐：默认只看总览和问题；想细看时可展开"待审核数据"全表。
